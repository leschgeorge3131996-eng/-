# 检索模型对照：纯词法 vs 本地 bge-small vs 云端 bge-m3 · 2026-06-03

> 缘起：泛化测试的头号弱点"过度拒答"集中在**英文公式 / 多语混排**文档。本实验回答
> "端侧为什么用 91MB 的小模型、换更大的有没有用"——在过度拒答最集中的两个文档
> （`attention_is_all_you_need` 英文论文 + `multilingual_contract_v6` 多语合同）的全部
> **22 题**上，三方对照检索器（答题 `deepseek-v4-flash`，判分 `qwen3-235b` 源接地 + 人复核）。

## 结果（单调改善、零回归）

| 检索器 | 维度 | 部署 | 22 题通过 |
|---|---|---|---|
| 纯词法（IDF+intent 词表） | — | — | 15/22 |
| 本地 **BGE-small-zh-v1.5** | 512 | 本地 91MB CPU，零云依赖 | 18/22（+3） |
| 云端 **bge-m3** | 1024 | 多语，本次走平台 API | **20/22（+5，较 small 再 +2）** |

逐题 `纯词法→bge-small→bge-m3`（救回标 `<<`）：
- `attention:gen_ans_1`（注意力公式）F→P→P
- `attention:gen_ans_3`（表1复杂度）F→P→P
- **`attention:gen_ans_6`（解码器如何掩盖未来位置）F→F→P** ← bge-m3 比 small 多救
- `multilingual_contract:gen_ans_3`（日语截止日）F→P→P
- **`multilingual_contract:gen_ans_4`（夜间支持需法律团队预批）F→F→P** ← bge-m3 多救
- **零回归**：没有任何 P→F。

bge-m3 剩 2 个未过（`gen_ans_0` 编码器/解码器层数、`gen_ans_2` BLEU 双值）——是**理解题 / 可辩护答案**，非检索召回问题。

## 结论与口径

1. **更大的多语模型（bge-m3）确实更能治英文/多语弱区**：15→18→20 单调升、零回归，bge-m3 较 bge-small 在最难的英文/多语召回上多救 2 题。**用户"为什么不用大的"的直觉是对的——大的有用。**
2. **但"端侧用小模型"是有意的设计取舍，不是偷懒**：
   - BGE-small 91MB、纯 CPU、零云依赖 → **真·可下沉到任意边缘节点**，这正是赛题"端侧/云端协同"的卖点；bge-m3 本地版约 2.3GB，更重、CPU 更慢，"端侧轻量可部署"的故事会打折。
   - 本次 bge-m3 走的是**云端 API**（≠ 本地零云依赖）；要保住"端侧"口径，需下其本地 ONNX 再验 CPU 延迟。
3. **诚实定位**：bge-small = **可部署的端侧选择**（轻、已验证、对锁定中文 demo 持平）；bge-m3 = **召回更强的升级选项**（多语/英文场景）。我们把这个取舍**量化刻画清楚了**，这是设计严谨性的体现，而非"只会塞个小模型"。

## 建议（交付前两周）

- **demo 仍用 BGE-small**：轻、已验证安全（固定集开=关）、契合"端侧轻量"叙事；现场即兴英文/多语论文时它也已能把过度拒答 6→1。
- **bge-m3 作为"已基准测试的升级路径"对外讲**：证明我们探索过设计空间、量化了取舍。若赛后要做多语强场景，再下本地 bge-m3 替换。
- 不在交付前两周把 2.3GB 的 bge-m3 仓促换进 live 端侧（需重验 CPU 延迟 + 重跑评测，风险>收益）。

## Codex 独立复核 + 最终决策（2026-06-03）

`codex exec` 独立读了本报告与 `edge_ab_generalization_20260602.md`（核对了行号），结论与上文一致并补了更优口径：

**最终决策：选 A（demo/live 维持本地 `bge-small`），但答辩按"第三方案口径"讲。**
- **理由**：① bge-m3 收益窄（英文/多语多救 2 题），demo 锁定中文、bge-small 已安全；② 两周内换 2.3GB 本地模型需重验 CPU 延迟/内存/评测回归，风险>收益；③ 维持"端侧轻量·零云依赖·已验证"才符合"诚实>刷分"。
- **第三方案口径（最优叙事）**：**端侧默认 `bge-small`（轻、零云依赖）+ `bge-m3`/reranker 作为"已基准测试的可选云端/赛后本地增强"，按文档语言/类型触发**（中文常规走端侧；英文论文/多语合同/公式表格密集时可上更强召回）。一举拿到：端侧协同真实 + 设计空间探索充分 + 对英文/多语弱点诚实补强。
- **必须守的诚实口径（codex 标的风险）**：① **不得**把"云端 API bge-m3 的 20/22"说成"本地端侧 bge-m3 已可交付"——本地 ONNX 的延迟/内存/量化/部署包体/现场稳定性**尚未闭环**；② 答辩**别**说"端侧显著提升"或"无副作用"，应说"固定中文 demo 持平安全；英文/多语/公式弱区降低过度拒答；总体净增益有限但真实可复核"。
