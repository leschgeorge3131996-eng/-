# 研答通 一页式项目说明

## 一句话定义

研答通是一个**端云分层协同**的论文/报告阅读与答辩准备助手：端侧/近端完成解析、切块、检索与证据定位，只把必要片段上云交由无问芯穹大模型推理，每条 `ask` 回答都能带证据回链、跳回 PDF 原页。

## 作品定位

- 作品形态：面向论文与报告阅读、答辩准备的文档助手（赛题一评选对象画像中的"个人智能助理"）
- 协同形态：**端侧/云端协同**——端侧/近端做解析/切块/检索/证据 bbox 定位，云端（无问芯穹 MaaS）只做必要片段的大模型推理；Token 压缩（长文档 ask 平均省 86.6%）即协同的量化收益
- 当前载体：Web 应用（评审演示形态）
- 目标场景：论文精读、报告复核、答辩准备

## 目标用户

- 需要精读论文、复核报告的学生与研究者
- 需要准备答辩、汇报的作者与主讲人

## 核心痛点

1. 长文阅读成本高，重点分散，用户很难快速把握关键信息。
2. 传统聊天工具脱离文档上下文，回答缺少依据，难以验证。
3. 答辩与复核需要的是"说得出处"，而不仅仅是"回答流畅"。

## 当前核心能力

### 输入层

- 支持上传 `TXT / Markdown / PDF`
- 保留文档原始文件、本地解析文本、页级结构化结果和文本分块结果

### 智能处理层

- 摘要：生成结构化摘要
- 问答：基于轻量检索选取相关片段，再调用模型回答
- 提纲：围绕文档内容生成汇报或答辩提纲

### 可解释性与工程能力

- `ask` 已支持结构化引用依据，返回页码与证据片段
- `summary / outline` 已支持来源片段展示
- 本地日志记录耗时、模型、token、结果类型、检索状态
- 统计面板可展示请求数、有效回答数、拒答数、错误数和延迟

## 差异化的落地方式

研答通的核心不是"文档 + 模型"的拼接，而是围绕"答案必须能回链到原文"这一个强约束做的一条完整链路：

1. **页级结构化解析**（PyMuPDF）保留每页的 block / line / bbox
2. **文本分块 + 轻量检索** 让 `ask` 只基于相关片段作答
3. **模型声明引用依据**：返回 `used_chunk_ids` 与 `evidence_quotes`，后端反查原文做二次校验
4. **PDF 内证据定位**：引用片段在原 PDF 页面内直接显示坐标高亮，并在旁附原文片段文本

任一环节未命中，系统显式拒答而不是编造——这是"证据可验证"的工程底座。

## 当前成果

- 端到端链路已在真实论文上跑通：上传 → 解析 → 检索 → 生成 → 打开定位 → PDF 内高亮 + 原文片段回显
- 后端测试覆盖 81 项核心服务与 API 路径（含 agentic 检索循环、引用不可伪造、bbox 回链）
- 前端测试覆盖上传 / 问答 / 证据跳转等主链路（14 项）
- 样例复跑报告与日志摘要可在 `evidence/` 目录下复现
- 当前已锁定中文论文 gold-sample candidate，并完成：
  - 主 QA 模型 / fallback 模型比较
  - 锁定候选题集的真实 replay 刷新

## 当前边界

- 当前最强、最适合比赛主讲的能力是 `ask -> citation -> PDF -> refusal`
- `summary / outline` 已可用，但证据语义仍弱于 `ask`
- 当前材料更适合受控评审演示，不按开放 SaaS 口径对外承诺

## 封板重点

1. 固化平台使用证据、硬证据摘要和评分映射
2. 把锁定题组统一收口到 PPT、视频、海报和答辩口径
3. 继续做小范围稳定性优化与更严格复现，但不再扩产品范围
